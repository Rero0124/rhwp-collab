# cc-rhwp 공동편집 설계 — 3단계: 실사용 기반

2단계(`docs/collab-stage2.md`)까지는 같은 브라우저 환경에서 동시 편집을 검증했다. 3단계는 실제 사용자가 쓸
수 있게 하는 기반이다. **원칙: rhwp 에 이미 있는 것은 가져다 쓰고, 우리는 "어디서·언제 돌리느냐"만 만든다.**

시작 조건: 2단계 R13·R14·R10 완료. 설계 변경은 이 문서를 먼저 고친다. 막히면 설계 세션(`cc-rhwp-2a`)에 묻는다.

| 순서 | 작업 | rhwp 에서 가져다 쓰는 것 | 우리가 만드는 것 |
|---|---|---|---|
| S3-1 | 글꼴 환경 고정 + 기기 간 시험 | 내장 웹 글꼴 36종, Rust 글꼴 배치 규칙(830개), 로컬 글꼴 허락 구조 | 공동편집 중 "내장 글꼴만" 설정, 브라우저·OS 간 시험 |
| S3-2 | 서버 정본 (검증) | 편집 함수의 오류 처리, WASM 그대로 | 서버가 같은 엔진으로 문서를 들고 기록 전에 먼저 적용 |
| S3-3 | 영속 저장 | 내보내기(저장) | 편집 기록 디스크 기록, 주기 저장, 재시작 복원 |
| S3-4 | 재접속 | 없음(rhwp 는 서버 연결 개념이 없는 오프라인 앱) | 끊긴 동안 편집 보관, 다시 붙으면 따라잡기 |
| 나중 | 내 편집만 되돌리기 | — | 보정을 거친 역연산 (오래 걸려 별도 단계) |

## S3-1 글꼴 환경 고정 + 기기 간 시험

- 목표: 운영체제·브라우저가 달라도 같은 문서·같은 편집이 같은 조판과 같은 digest 를 낸다. 그러면 2단계의
  "같은 환경 전제" 한계(조판 의존 연산 `layout`, digest 비교)가 함께 풀린다.
- rhwp 구조: 웹 글꼴은 `assets/fonts/` 의 WOFF2 36종(`mydocs/tech/font_fallback_strategy.md`), 조판 이름·
  메트릭 규칙은 `assets/font-rules/font_rule_registry.json` 에서 생성. 로컬 글꼴은 Local Font Access 허락과
  `loadStoredLocalFonts()`(예전에 허락한 글꼴 스냅샷)로 들어온다.
- 할 일:
  1. 공동편집 중에는 **로컬 글꼴을 쓰지 않는다.** 0002 패치로 플러그인 API `host.setFontPolicy('bundled-only')`
     를 두고, 공동편집 열기 전에 건다(해제 함수는 원장 회수). studio 의 글꼴 환경 준비
     (`declared-font-environment.ts`, `local-fonts.ts`)가 이 정책일 때 로컬 후보를 건너뛰게 한다.
  2. **조판이 브라우저 측정값을 쓰는 곳이 있는지 조사한다**(예: canvas `measureText` 로 잰 값을 코어에
     넣는 `canvas_metrics` 경로). 내장 글꼴만 써도 브라우저 측정이 조판에 들어가면 브라우저마다 달라진다.
     그런 경로가 있으면 공동편집에서 끌 수 있는지 보고, 못 끄면 설계 세션에 보고한다.
  3. 글꼴 정책을 엔진 지문(2단계 §7)에 넣는다.
- 시험: 서로 다른 브라우저 엔진(Chrome·Firefox·WebKit, puppeteer/playwright)과 가능하면 다른 OS(Linux
  컨테이너의 headless Chrome)에서 샘플 문서 열기 + 같은 편집 열(2단계 R8 시나리오, `layout` 연산 포함) →
  digest 비교. **합격: 엔진 2종 이상에서 전부 일치.** 어긋나면 어느 문단·어느 값에서 갈리는지 좁혀 §기록에
  남긴다. 원인이 rhwp 라면 재현 정보만 정리하고 업스트림 보고는 사용자가 정한다.
- 합격하면 2단계 §9 의 "`layout` 연산은 기기가 다르면 결과가 달라질 수 있다" 한계를 지운다.

## S3-2 서버 정본 (검증)

- 서버가 방마다 **같은 엔진(TS 엔진 + rhwp WASM)으로 정본 문서를 들고 있는다.** Node 에서 그대로 돈다(R5
  시뮬레이션이 이미 그렇게 돈다).
- **기록 전 검증:** `ops` 묶음이 오면(base 가 맞을 때) 정본에 먼저 적용한다(기록 끔). rhwp 가 오류를 내면 그
  묶음을 기록하지 않고 보낸 쪽에 `{type:"invalid", reason}`. 보낸 쪽은 재동기화한다(드문 경우라 단순하게).
  `state` 기록도 `collabLoadState` 로 먼저 적재해 본다.
- **패닉 격리:** rhwp 가 오류 대신 패닉하면 그 WASM 인스턴스 메모리를 더는 믿을 수 없다. 방마다
  `worker_thread` 에 정본을 두고, 패닉하면 그 묶음을 `invalid` 로 거절하고 워커를 버린 뒤 디스크(S3-3)에서
  다시 만든다.
- **digest 기준점:** 서버가 seq 마다 정본 digest 를 갖고 있으므로, 클라이언트 보고를 "처음 보고한 값" 대신
  **서버 값과 비교**한다. 다르면 그 클라이언트에만 재동기화를 시킨다(지금은 방 전체에 `diverged`).
- 늦은 참여·재동기화의 `welcome` 은 정본에서 만든다(마지막 `state` 기준점 대신 체크포인트 + 그 뒤 기록, S3-3).

## S3-3 영속 저장

- 방 디렉터리: `doc.<hwp|hwpx>`(체크포인트, `collabExportState` 의 원본 형식 규칙), `log.jsonl`(체크포인트
  뒤 기록), `meta.json`(체크포인트 seq, 엔진 지문, 원본 형식).
- **편집 기록은 매 묶음 디스크에 덧붙이고 fsync** 한 뒤에 방송한다(방송했는데 디스크에 없는 기록이 생기지
  않게). 가볍다.
- **파일 저장(체크포인트)은 주기적으로:** 마지막 편집 뒤 5초 잠잠할 때, 또는 200 묶음마다, 마지막 참여자가
  나갈 때, 서버 종료 때. 임시 파일에 쓰고 rename(원자적), 그다음 기록을 비운다. 매 편집마다 파일 전체를
  쓰지 않는 이유: 큰 문서는 내보내기 한 번에 수십 ms·수 MB(2단계 R9).
- 시작·첫 참여 때 복원: 체크포인트 적재 → 기록 재생 → 정본 digest 기록.
- **업그레이드:** 편집 기록은 엔진 버전에 묶이고(같은 함수 = 같은 결과), 체크포인트 파일은 버전과 무관하다.
  그래서 엔진을 올리기 전에 모든 방을 체크포인트하고 기록을 비운다. 새 엔진은 파일에서만 시작한다.
- 저장소는 인터페이스(`DocStore`)로 두고 로컬 디스크 구현만 만든다. 다른 저장소(파일 서버 원본 경로 등)는
  다운스트림 결정.
- 첫 방 생성: 지금처럼 첫 참여자의 base → 체크포인트로 쓴다.

## S3-4 재접속

- 끊기면 지수 백오프로 다시 붙는다. 엔진 상태(`unconfirmed`, `lastSeq`)는 그대로 둔다. 끊긴 동안의 편집은
  계속 `unconfirmed` 에 쌓인다. 화면에 "연결이 끊겼습니다. 편집은 다시 연결되면 보내집니다".
- 다시 붙을 때 `hello` 에 `lastSeq` 를 싣는다. 서버는:
  - `lastSeq` 가 기록 범위 안이면 `{type:"catchup", entries}`(그 뒤 기록) → 클라이언트는 원격 수신으로 처리
    (되감기·보정) → `requeue` → flush.
  - 범위 밖(체크포인트로 비워짐)이면 일반 `welcome` → 재동기화(미확정 취소, 알림).
- **끊기는 순간 보낸 묶음의 운명을 모른다.** 그래서 보내는 묶음마다 `batchId`(clientId + 순번)를 붙이고 서버
  기록에도 남긴다. `catchup` 에 내 `batchId` 가 있으면 남의 편집이 아니라 **확정(ack)** 으로 처리한다(중복
  적용 방지).
- 오래 끊기면 충돌이 늘어난다(2단계 §4 규칙 그대로). 미확정이 많거나(예: 2,000건) 오래 끊기면(예: 10분)
  미리 알린다.

## 관문

- S3-1: 브라우저 엔진 2종 이상에서 digest 전부 일치.
- S3-2: 잘못된 인자·범위 초과·패닉 유발 묶음을 주입해도 거절되고 방은 계속된다. 패닉 뒤 워커 재생성.
  서버 digest 기준 비교로 어긋난 클라이언트만 재동기화.
- S3-3: 편집 중 서버를 강제 종료(kill -9) → 재시작 → fsync 된 마지막 묶음까지 손실 없음, 복원 digest 가 종료
  직전과 같음. 업그레이드 절차 시험.
- S3-4: 동시 편집 중 연결 끊기·지연 → 재접속 → 수렴. 끊기기 직전 보낸 묶음이 서버에 받아졌던 경우 중복 없음.
  오래 끊김 → 재동기화 + 알림.
- **R5 시뮬레이션 확장:** 서버 정본·무작위 연결 끊김·서버 재시작을 섞어 시드 500 × 200 에서 수렴 실패 0.
