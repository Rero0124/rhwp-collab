# 공동편집 4단계: 사용자별 되돌리기 (안전한 되돌리기)

3단계(`docs/collab-stage3.md`)까지로 공동편집은 끝까지 돈다. 지금은 공동편집 중 studio 되돌리기가 꺼져 있다
(0002 패치의 `suspendHistory`). 이 단계는 그것을 **내 편집만, 안전할 때만** 되돌리도록 켠다.

## 1. 사용자 결정 (2026-11-27)

- 내 편집만 되돌린다. 다른 사람의 편집은 건드리지 않는다.
- 내 편집 뒤에 다른 사람이 **같은 자리**를 고쳤으면 그 단계는 되돌리지 않는다. "다른 사람이 이후에 고친
  부분이라 되돌릴 수 없습니다" 를 알리고 그 단계는 버린다.
- 겹치지 않으면 혼자 편집할 때처럼 되돌아간다.
- 배경: 겹친 자리를 무조건 되돌리면 의도와 다른 결과가 나온다(Google Docs 식 "항상 되돌림"은 택하지 않음).

## 2. 출발점: studio 의 되돌리기를 그대로 쓴다

- studio 는 명령 37종(`rhwp-studio/src/engine/command.ts`)이 각자 `undo()` 를 갖고, `engine/history.ts` 가
  undo/redo 스택을 관리한다. 입력 묶기(연속 타이핑 = 한 단계)도 studio 규칙을 쓴다.
- 명령의 `undo()` 는 WASM export 를 부른다(`deleteText`·`insertText`·`mergeParagraph`·`setCharShapeRuns`·
  `restoreDeleteFragment`·`restoreSnapshot` 등). 2단계의 export 경계 기록이 이 호출을 그대로 op/state 로 보낸다.
  **되돌리기를 위한 새 동기화 경로는 없다.** 수렴은 기존 장치(되감기·보정·서버 순서)가 그대로 보장한다.
- 새로 할 일은 세 가지다: ① 명령이 기억한 위치를 남의 편집에 맞춰 옮기기, ② 겹치면 막기, ③ 내 편집이
  충돌로 버려지면 그 명령도 스택에서 빼기.

## 3. 규칙

### 3.1 위치 옮기기
- 명령이 기억한 위치(구역·문단·글자, 셀 경로 포함)는 원격 기록이 들어올 때마다 그 기록의 지도로 옮긴다.
  캐럿을 옮기는 것과 같은 지도(`collabMapCaret` 계열)다. undo 스택과 redo 스택 모두.
- 다른 문단에서 문단 수가 바뀌는 편집(남의 Enter 등)은 인덱스만 옮기고 막지 않는다.

### 3.2 막기 (명령마다 "발자국" = 고친 문단 범위, 구조 명령은 구역)
명령 C 뒤에 들어온 원격 기록 R 중 하나라도 아래에 해당하면 C 는 막힘이다.
1. R 이 C 의 발자국 문단(셀 문단 포함)을 고쳤다 — 텍스트·서식 모두. (동시 편집 보정 §4.4 는 같은 문단의
   동시 입력을 합쳐 주지만, 되돌리기는 더 보수적으로 같은 문단이면 막는다.)
2. R 이 구조 편집·state 이고 C 와 같은 구역이다(2단계 §4.5 표의 "같은 구역" 정의).
3. C 가 스냅샷으로 되돌리는 명령(`SnapshotCommand`·`Submode*SnapshotCommand`, `restoreSnapshot` 류)이고 R 이
   **무엇이든** 있다 — 스냅샷 복원은 그사이 남의 편집까지 지운다.
4. C 의 되돌리기가 저장소에 의존하는 호출(`restoreDeleteFragment` 등, state)이고 R 이 같은 구역이다.

- 막힌 명령을 되돌리려 하면: 알림을 띄우고 그 명령을 스택에서 버린다(문서는 그대로). 다음 되돌리기는 그 아래
  명령으로 간다. 한 번 누름에 여러 단계를 건너뛰지 않는다(왜 안 됐는지 보이게).
- redo 도 같은 규칙. 새 로컬 편집이 생기면 redo 스택은 studio 규칙대로 비운다.

### 3.3 버려진 편집
- 내 미확정 편집이 충돌로 버려지면(엔진 `droppedEntries`, 꼬리 포함) 그 편집을 만든 명령도 스택에서 뺀다.
  그 명령의 기록 항목이 일부라도 버려졌으면 명령 전체를 뺀다. 그러려면 명령 ↔ 만든 기록 항목의 연결을 둔다.
- 되돌리기·다시 하기가 만든 기록이 버려지면 그 명령을 버린다(알림: "되돌리기가 다른 사람 편집과 겹쳐
  취소됐습니다").

### 3.4 스택을 비우는 때
- 제자리 재동기화·welcome(재접속 범위 밖, 세대 전환)·문서 교체: 위치가 의미를 잃으므로 비운다.
- catchup(재접속 범위 안): 원격 수신과 같으므로 3.1~3.2 로 처리하고 비우지 않는다.

  - 표에 없는 type(업스트림이 나중에 더한 명령 포함)은 3.2-3 으로 처리한다(뒤에 원격이 하나라도 있으면 막음). "지원 기능은 빠르게, 새 기능은 느리지만 지원"과 같은 원칙이다.

## 6. U3: snapshot 경로의 문단 범위 복원 (2026-11-27 착수, 새 코드 세션 cc-rhwp-f6)

- **대상:** studio 가 문서 전체 스냅샷으로 되돌리는 명령(`SnapshotCommand` 계열, 호출처 89곳: 표·붙여넣기·개체 삭제·
  대화상자 등) 가운데, 만든 기록의 발자국이 **한 구역의 문단 범위**로 특정되는 것. 구역 전체·문서 전체 발자국(쪽 설정 등)은
  지금처럼 3.2-3 이다.
- **막힘 판정:** 명령의 발자국 문단(전·후 범위)을 남이 고치지 않았고(fate 가 Kept), 범위 앞의 문단 수 변화는 지도로 옮길 수
  있으면 허용한다. 같은 구역의 다른 곳에 있는 남의 구조 편집(다른 곳에 표 만들기 등)은 막지 않는다(3.2-2 를 이 경우만 풂).
- **복원:** collab-core 보조가 그 명령의 스냅샷에서 "명령 전" 문단 범위를 가져와, 지금 문서에서 지도로 옮긴 "명령 후" 범위를
  바꾼다. redo 는 undo 때 뜬 스냅샷으로 반대 방향을 한다.
  - `collab*` 보조는 기록 훅 대상이 아니므로, 복원 뒤 엔진이 결과를 state 항목으로 직접 기록한다. 그 state 는 6단계 S1 에
    따라 서버가 다시 써서 모두에게 보낸다.
  - 전제 확인: 스냅샷 문단이 참조하는 DocInfo 항목(글자·문단 모양, 테두리·배경, 번호, 스타일, BinData)이 지금 문서에 같은
    번호·같은 내용으로 있어야 한다. 다르면 그 단계는 막는다(안내).
- **범위 표시가 붙은 state (2026-11-27 결정):** 복원 결과를 그냥 state 로 보내면, 받는 쪽 보정 규칙(§4.5: state 는
  모든 미확정과 충돌)에 따라 그 순간 왕복 중이던 다른 참여자의 입력이 취소된다. B 가 계속 치고 있으면 A 가 되돌릴 때마다
  B 의 마지막 글자들이 사라지는 셈이라 받아들일 수 없다. 그래서 복원 state 에 범위 표시
  `range: {section, lo, before, after}`(문단 수)를 싣는다.
  - 받는 쪽: 그 state 를 "구역 section 의 [lo, lo+before) 를 after 개 문단으로 바꾼 구조 편집"(발자국 anchor=lo, pd=after-before)
    으로 보고 보정한다. 범위 밖 미확정은 번호만 옮겨 살리고, 범위 안이면 충돌이다. 다른 참여자의 되돌리기 스택도 문서 전체로
    막지 않고 같은 지도로 옮긴다.
  - 서버 정본: 범위 표시가 거짓이면 다른 참여자의 문서를 잘못 보정하게 된다. 그래서 적용 뒤 확인한다. 다른 구역은 같아야
    하고, 그 구역은 범위 밖 문단이 적용 전과 같아야 한다(번호만 밀림). DocInfo 는 덧붙이기만 허용하고, 그 밖의 문서 부분도
    같아야 한다. 맞지 않으면 `invalid {reason:"range"}` 로 거절한다(정상 클라이언트는 언제나 맞음).
    S1 다시 쓰기 뒤에도 모델이 같으므로 범위 표시는 그대로 유효하다.
- **구현 결정 (2026-11-27, 설계 세션 승인):**
  - 범위는 실행이 만든 기록 열로 정한다(명령 type 목록이 아니다): 본문·셀 글자 연산, 역할 있는 서식, 발자국 있는 구조 연산이
    한 구역의 연속 문단으로 모이면 범위다. 실행 직후 스냅샷과 지금 문서의 문단 수가 그 범위와 맞는지, 명령이 기존 DocInfo
    항목을 고치지 않았는지 확인한다(아니면 3.2-3).
  - 막힘: 범위 안을 무엇이든 고친 남의 기록(표 칸 편집·개체 단위 구조 편집 포함 — 범위 바꾸기가 그 표를 통째로 지운다),
    발자국 없는 구조, 구역 모르는 문서 단위 기록, state 는 막는다. 범위 밖 구조 편집은 번호만 옮긴다. DocInfo 정의만 고치는
    서식(`updateStyle`·`updateStyleShapes`·`setNumberingCharShape`)은 범위에 닿지 않는다고 보고 DocInfo 전제가 거른다.
  - **범위가 있는 명령은 남의 기록이 있든 없든 언제나 범위 복원 + 범위 표시로 한다**(처음 Q4 의 "남의 기록이 없으면 문서
    전체 복원"을 바꿈). 문서 전체 복원 결과는 범위 표시를 달 수 없어(명령이 덧붙인 DocInfo 항목까지 지운다) B 가 막 치기
    시작한 순간의 입력을 취소하기 때문이다. 명령이 덧붙인 DocInfo 항목은 쓰이지 않은 채 남는다(BinData 는 S1 이 버린다).
    문서 전체 복원은 범위가 없는 스냅샷 명령(3.2-3)에만 쓴다. 플러그인 스위치(`rangeRestore: 'remote'`)로 예전 동작을 고를 수
    있다.
  - DocInfo 전제는 목록 전체의 "덧붙이기만"(참조한 항목만 보지 않음 — 목록끼리 서로 참조해 닫힘을 구해야 한다). 어긋나면
    "문서의 서식 목록이 바뀌어 이 단계는 되돌릴 수 없습니다"(원인이 남의 편집이 아니므로 따로 안내).

    문단·DocInfo 를 collab-core 에 따로 떠 둔다 — redo 원본 스냅샷은 studio 가 redo 직후 지운다. 확정·버림·리셋 때 푼다).
  - Rust 는 `collab-core/src/undo_restore.rs`(`ot` 의 자식 모듈 — 분류·발자국을 다시 쓴다, JS 표면도 이 파일)와 `ot.rs` 의
    작은 변경(발자국 `span`, 범위 표시 state 읽기)으로 하고 `lib.rs`·`wasm.rs` 는 고치지 않는다.
- **시험:** A 가 표 만들기·붙여넣기·개체 삭제 뒤 B 가 같은 구역의 다른 문단을 편집(글자·구조) → A 되돌리기가 허용되고 A 의
