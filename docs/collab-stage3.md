# cc-rhwp 공동편집 설계 — 3단계: 실사용 기반

2단계(`docs/collab-stage2.md`)까지는 같은 브라우저 환경에서 동시 편집을 검증했다. 3단계는 실제 사용자가 쓸
수 있게 하는 기반이다. **원칙: rhwp 에 이미 있는 것은 가져다 쓰고, 우리는 "어디서·언제 돌리느냐"만 만든다.**

시작 조건: 2단계 R13·R14·R10 완료. 설계 변경은 이 문서를 먼저 고친다. 막히면 설계 세션(`cc-rhwp-2a`)에 묻는다.

| 순서 | 작업 | rhwp 에서 가져다 쓰는 것 | 우리가 만드는 것 |
|---|---|---|---|
| S3-1 | 글꼴 환경 고정 + 기기 간 시험 | 내장 웹 글꼴 36종, Rust 글꼴 배치 규칙(830개), 로컬 글꼴 허락 구조 | 공동편집 중 "내장 글꼴만" 설정, 브라우저·OS 간 시험 |
| S3-2 | 서버 정본 (검증) | 편집 함수의 오류 처리, WASM 그대로 | 서버가 같은 엔진으로 문서를 들고 기록 전에 먼저 적용 |
| S3-3 | 영속 저장 | 내보내기(저장) | 편집 기록 디스크 기록, 주기 저장, 재시작 복원 |
| S3-4 | 재접속 | 없음(rhwp 는 서버 연결 개념이 없는 오프라인 앱) | 끊긴 동안 편집 보관, 다시 붙으면 따라잡기 |
| 나중 | 내 편집만 되돌리기 | — | 보정을 거친 역연산 (오래 걸려 별도 단계) |

## S3-0 digest 에 BinData 포함 (2단계 마무리에서 발견, S3-1 전에)

- 현상: digest(`doc_info_model_digest` + `section_model_digest`)가 `Document.bin_data_content`(그림·OLE·차트
  바이트)를 보지 않는다. 차트 데이터 편집이 성공해도 digest 가 그대로라, BinData 만 갈리면 digest 보고가 못 잡고
  동작 동일성 검사(R1b)도 그 기능의 사례를 세지 못한다. S3-2 의 서버 기준 비교도 같은 사각을 갖게 된다.
- 결정: **넣는다.** digest = 기존 두 지문 + BinData 항목별 해시(id 순).
  - ~~항목 해시는 저장된 표현 그대로~~ → **개정: 압축을 푼 내용의 blake3** (코드 세션 측정 결과로 변경).
    편집한 항목은 표현이 바뀐다: 차트를 편집한 쪽은 `Loaded`(비압축)를 들고, 그 결과를 내보내 다시 읽은 쪽은
    압축된 원본 스트림을 든다. 2단계 프로토콜은 모두 같은 바이트·같은 연산에서 출발하므로 표현도 같아지지만,
    3단계에서는 체크포인트 파일로 들어온 참여자·재시작한 서버가 기존 참여자와 다른 표현을 갖게 되어 digest 가
    거짓으로 어긋나고 서버 기준 비교에서 재동기화가 반복된다. **원칙: digest 는 저장 표현이 아니라 내용을 본다.**
  - 압축 해제 비용 줄이기:
    - `(bin_data_epoch, id)` → 항목 해시 캐시.
    - `Lazy` 이면서 원본 저장 바이트가 있는 항목: `blake3(압축 여부 + 저장 바이트)` → 내용 해시 메모를
      `CollabCore` 에 둔다. 편집하지 않은 항목은 내보내기→다시 읽기 뒤에도 저장 바이트가 같으므로(코드 세션이
      샘플 5종 2회 왕복으로 확인) 적재·되감기·재접속 뒤에도 메모가 맞고, 압축 해제는 항목마다 세션에 한 번이다.
    - `Loaded`·메모리 공유 항목은 이미 풀린 바이트라 그대로 해시한다.
    - 되감기마다 epoch 가 올라 저장 바이트 해시가 반복되는 비용은 blake3 로 수 ms 수준으로 본다. 리졸버
      `Weak` 키 메모 같은 추가 캐시는 **측정해서 필요할 때만** 넣는다: 큰 그림 문서에서 되감기 직후 digest 가
      20ms 를 넘으면.
  - **캐시:** 항목별 해시를 `(bin_data_epoch, id)` 로 캐시한다. 업스트림 계약상 바이트를 제자리에서 바꾸는 곳은
    `bump_bin_data_epoch()` 를 부르는 곳뿐이다(문서 교체·새 문서·`set_document`·차트 편집·문단 블록 가져오기·외부
    붙여넣기). 추가는 append-only 라 새 id 만 해시하면 된다. `collabLoadState`·자체 스냅샷 복원도 epoch 를 올린다
    (업스트림 복원과 같은 설치 순서). 시험: 차트 데이터 편집 → digest 바뀜, 같은 편집을 상대에 재생 → 다시 같음,
    큰 그림 문서에서 두 번째 digest 가 캐시로 빨라짐, **차트 편집 뒤 내보내기→다시 읽은 쪽과 digest 같음,
    다시 읽은 뒤 첫 digest 가 메모로 압축을 풀지 않음**, 큰 그림 문서의 되감기 직후 digest 시간 기록.
  - `extra_streams`·`hwpx_aux_entries`(라운드트립 보존용 원본 조각)는 편집으로 바뀌지 않으므로 넣지 않는다.
- R1b 재실행: BinData 를 보게 된 digest 로 차트 사례(`setChartDataByIndex` 등)를 다시 센다.

## S3-1 글꼴 환경 고정 + 기기 간 시험

- 목표: 운영체제·브라우저가 달라도 같은 문서·같은 편집이 같은 조판과 같은 digest 를 낸다. 그러면 2단계의
  "같은 환경 전제" 한계(조판 의존 연산 `layout`, digest 비교)가 함께 풀린다.
- rhwp 구조: 웹 글꼴은 `assets/fonts/` 의 WOFF2 36종(`mydocs/tech/font_fallback_strategy.md`), 조판 이름·
  메트릭 규칙은 `assets/font-rules/font_rule_registry.json` 에서 생성. 로컬 글꼴은 Local Font Access 허락과
  `loadStoredLocalFonts()`(예전에 허락한 글꼴 스냅샷)로 들어온다.
- 할 일:
  1. 공동편집 중에는 **로컬 글꼴을 쓰지 않는다.** 0002 패치로 플러그인 API `host.setFontPolicy('bundled-only')`
     를 두고, 공동편집 열기 전에 건다(해제 함수는 원장 회수). studio 의 글꼴 환경 준비
     (`declared-font-environment.ts`, `local-fonts.ts`)가 이 정책일 때 로컬 후보를 건너뛰게 한다.
  2. **조판이 브라우저 측정값을 쓰는 곳이 있는지 조사한다**(예: canvas `measureText` 로 잰 값을 코어에
     넣는 `canvas_metrics` 경로). 내장 글꼴만 써도 브라우저 측정이 조판에 들어가면 브라우저마다 달라진다.
     그런 경로가 있으면 공동편집에서 끌 수 있는지 보고, 못 끄면 설계 세션에 보고한다.
  3. 글꼴 정책을 엔진 지문(2단계 §7)에 넣는다.
- 시험: 서로 다른 브라우저 엔진(Chrome·Firefox·WebKit, puppeteer/playwright)과 가능하면 다른 OS(Linux
  컨테이너의 headless Chrome)에서 샘플 문서 열기 + 같은 편집 열(2단계 R8 시나리오, `layout` 연산 포함) →
  digest 비교. **합격: 엔진 2종 이상에서 전부 일치.** 어긋나면 어느 문단·어느 값에서 갈리는지 좁혀 §기록에
  남긴다. 원인이 rhwp 라면 재현 정보만 정리하고 업스트림 보고는 사용자가 정한다.
- 합격하면 2단계 §9 의 "`layout` 연산은 기기가 다르면 결과가 달라질 수 있다" 한계를 지운다.

### 결정: `bundled-only` = 조판은 엔진 기본 환경 (코드 세션 조사 결과로 구체화)

- 조사: 브라우저에 따라 달라지는 값이 모델(`line_segs`)에 들어가는 경로가 넷이다 — ① canvas 보충 측정
  (`measureText`, 로컬 글꼴과 무관하게 canvas2d 에서 항상 켜짐), ② 선언 글꼴 환경(`setFontEnvironment`: 로컬
  프로그램, 권한 없는 `local()` 존재 확인, 내장 woff2 프로그램(fetch 성공 여부), 사용자 글꼴 선호), ③ 네이티브
  OTF/PUA 공급, ④ `setDpi`(studio 미호출). "로컬 후보만 건너뛰기"로는 ②의 내장 woff2 메트릭이 남는데, Node 에는
  FontFace·fetch·woff2 해제가 없어 서버 정본(S3-2)·시뮬레이션과 갈린다.
- 결정: 공동편집 중 **조판은 엔진 내장 규칙(기본 환경)만** 쓴다(①②③ 끔: `setFontEnvironment(undefined)`,
  `selectCanvasMetrics(false)`). **표시는 내장 웹 글꼴만**(로컬 스냅샷·권한 안내·CanvasKit 로컬 face 생략). Node 와
  같은 환경이라 서버 digest 와 구성상 같아진다. 플러그인은 열린 문서에 정책이 실제로 먹었는지(`environmentId`
  null, `canvasMetricsActive` false) 확인하고 아니면 방에 들어가지 않는다. 정책은 엔진 지문(코드 해시)에 든다.
- **대가와 확인 조건:** 혼자 편집할 때(woff2 실제 폭 + canvas 보충 측정)보다 줄 나눔·쪽 나눔이 덜 정확할 수 있고,
  조판 폭(규칙 표)과 그리는 글자(woff2)가 미세하게 어긋나 보일 수 있다. 또 같은 문서가 공동편집 켬/끔에 따라
  다르게 배치될 수 있다. 그래서 S3-1 에서 **충실도 차이를 잰다**: 업스트림 샘플 묶음(글 위주·표·양식·한글 글꼴
  다양)에서 같은 문서를 기본 모드와 `bundled-only` 로 열어 쪽 수 차이, 줄 나눔이 다른 문단 비율, 글자 겹침·벌어짐
  눈 확인(스크린샷 몇 장)을 §기록에 남긴다.
  - 판단 기준: 쪽 수가 달라지는 문서가 있거나 줄 나눔이 다른 문단이 5% 를 넘으면 **대안 B** 를 검토한다 — 조판에
    내장 woff2 메트릭은 넣고(모든 기기가 같은 바이트) canvas 보충 측정만 끄며, Node 서버는 같은 woff2 를 디스크에서
    읽어 공급한다(woff2 해제 수단 필요). 그 기준 안이면 지금 결정 유지.
  - **판정 (2026-11-26): 유지.** 기준의 뜻은 "정확도가 떨어지는가"이고, 정답은 기본 모드가 아니라 **한컴이 저장한
    배치**(LineSeg·쪽 수)다. 쪽 수가 달라진 1건(hwp3-sample11)은 `bundled-only` 가 한컴 쪽 수(151)와 맞고 기본 모드가
    벗어났으므로 정확도 손실이 아니다. 줄 나눔이 다른 문단은 0.1%(여러 줄 0.3%)이고, 한컴 일치율은 모든 문서에서
    `bundled-only` ≥ 기본이다. 앞으로 이 기준은 "**`bundled-only` 가 한컴 저장 배치에서 기본 모드보다 더 벗어나는
    경우**"로 읽는다.
  - 측정하지 못한 경우(문서 글꼴이 실제로 설치되고 로컬 글꼴 권한을 준 사용자, 주로 Windows)는 판정을 바꾸지
    않는다. 로컬 글꼴은 기기마다 있고 없고가 달라서 서버·다른 참여자와 같은 결과를 낼 수 없다. 대안 B(내장 woff2)도
    로컬 글꼴을 쓰지 않으므로 이 차이를 메우지 못한다. 그래서 이것은 결정성의 본래 대가로 2단계 §9 알려진 한계에 옮긴다(`layout` 기기 차이 한계를 지울 때 이 줄로 바꾼다).
    "공동편집을 켜면 혼자일 때보다 배치가 달라질 수 있다"는 것을 사용자에게 알린다.
- 시험 범위: Chrome + WebKit(로컬에 이미 있는 Playwright 캐시)로 엔진 2종 관문을 채우고, **Node digest 와도
  일치**를 본다. Firefox·Linux 컨테이너는 내려받아야 하므로 하지 않는다(필요하면 사용자 허락 후).

## S3-2 서버 정본 (검증)

- 서버가 방마다 **같은 엔진(TS 엔진 + rhwp WASM)으로 정본 문서를 들고 있는다.** Node 에서 그대로 돈다(R5
  시뮬레이션이 이미 그렇게 돈다).
- **기록 전 검증:** `ops` 묶음이 오면(base 가 맞을 때) 정본에 먼저 적용한다(기록 끔). rhwp 가 오류를 내면 그
  묶음을 기록하지 않고 보낸 쪽에 `{type:"invalid", reason}`. 보낸 쪽은 재동기화한다(드문 경우라 단순하게).
  `state` 기록도 `collabLoadState` 로 먼저 적재해 본다.
- **패닉 격리:** rhwp 가 오류 대신 패닉하면 그 WASM 인스턴스 메모리를 더는 믿을 수 없다. 방마다
  `worker_thread` 에 정본을 두고, 패닉하면 그 묶음을 `invalid` 로 거절하고 워커를 버린 뒤 디스크(S3-3)에서
  다시 만든다.
- **digest 기준점:** 서버가 seq 마다 정본 digest 를 갖고 있으므로, 클라이언트 보고를 "처음 보고한 값" 대신
  **서버 값과 비교**한다. 다르면 그 클라이언트에만 재동기화를 시킨다(지금은 방 전체에 `diverged`).
- 늦은 참여·재동기화의 `welcome` 은 정본에서 만든다(마지막 `state` 기준점 대신 체크포인트 + 그 뒤 기록, S3-3).

## S3-3 영속 저장

- 방 디렉터리: `doc.<hwp|hwpx>`(체크포인트, `collabExportState` 의 원본 형식 규칙), `log.jsonl`(체크포인트
  뒤 기록), `meta.json`(체크포인트 seq, 엔진 지문, 원본 형식).
- **편집 기록은 매 묶음 디스크에 덧붙이고 fsync** 한 뒤에 방송한다(방송했는데 디스크에 없는 기록이 생기지
  않게). 가볍다.
- **파일 저장(체크포인트)은 주기적으로:** 마지막 편집 뒤 5초 잠잠할 때, 또는 200 묶음마다, 마지막 참여자가
  나갈 때, 서버 종료 때. 임시 파일에 쓰고 rename(원자적), 그다음 기록을 비운다. 매 편집마다 파일 전체를
  쓰지 않는 이유: 큰 문서는 내보내기 한 번에 수십 ms·수 MB(2단계 R9).
- 시작·첫 참여 때 복원: 체크포인트 적재 → 기록 재생 → 정본 digest 기록.
- **업그레이드:** 편집 기록은 엔진 버전에 묶이고(같은 함수 = 같은 결과), 체크포인트 파일은 버전과 무관하다.
  그래서 엔진을 올리기 전에 모든 방을 체크포인트하고 기록을 비운다. 새 엔진은 파일에서만 시작한다.
- 저장소는 인터페이스(`DocStore`)로 두고 로컬 디스크 구현만 만든다. 다른 저장소(파일 서버 원본 경로 등)는
  다운스트림 결정.
- 첫 방 생성: 지금처럼 첫 참여자의 base → 체크포인트로 쓴다.

### 결정 (2026-11-26): 계보 보존 — 위의 "체크포인트에서 welcome·복원"을 대체

- **발견(코드 세션):** 편집된 문서에서 내보내기→다시 읽기(R∘E)는 항등이 아니다. 편집으로 새로 생긴 부분의
  왕복 보존 필드·파생 비트(새 CharShape 의 attr·raw_data, 새 표의 attr·list_header_width_ref·raw_*_extra)는
  직렬화→파싱을 거쳐야 채워진다. 이 필드를 digest 에서 빼도 이후 연산 결과가 달라진다(시뮬레이션에서 문단
  수 차이). R5 `--s3` 시드 100 × 200: 체크포인트에서 시작하면 실패 36, 처음 base + 기록이면 0.
- **원칙:** 같은 방의 모든 문서(정본·참여자·늦은 참여자·재시작한 정본)는 **모두가 같은 바이트를 다시 읽은
  지점**에서 출발해 같은 기록을 재생해야 한다. 그런 지점을 **기준점**이라 한다.
  - 처음 base: 모든 참여자가 이 바이트를 읽고 시작한다.
  - 기록 안의 `state` 항목: 보낸 쪽도 자기 바이트를 다시 읽으므로(2단계 R6·자기 재적재) 이미 기준점이다.
  - 세대 전환 파일(아래).
  - 다시 읽지 않은 문서를 내보낸 파일은 기준점이 **아니다**.
- **welcome·재시작 복원 = 마지막 기준점 + 그 뒤 기록.** 2단계 R6 의 "마지막 state + 그 뒤 항목" 규칙을 그대로
  잇는다. 기록은 매 묶음 fsync 하므로 잃지 않는다. 세션 중 체크포인트로 기록을 비우지 않고, 서버 종료 때도
  비우지 않는다.
- **세대 전환**(기록을 비우는 유일한 길): 방이 일정 시간 빈 뒤에만 한다. 그 시간은 오래 끊김 기준과 같게
  10분이다. 순서는 다음과 같다.
  1. 정본을 내보낸다(E).
  2. 그 바이트를 새 `base` 로 원자적으로 쓴다.
  3. **정본도 그 바이트를 다시 읽는다**(R). 다시 읽지 않으면 정본만 옛 계보에 남는다.
  4. 기록을 비우고 `meta.json` 에 세대 번호와 기준 seq 를 남긴다.
  - 그 뒤 들어오는 사람은 모두 새 세대에서 시작한다. 그보다 오래 끊겼던 사람은 범위 밖이므로 welcome 으로
    재동기화되고 안내를 받는다(S3-4 그대로).
- **파일 둘:**
  - `base.<ext>`: 기준점. 복원은 이것만 쓴다.
  - `doc.<ext>`: 사용자가 보는 저장본. 사용자가 처음 말한 "원본 파일에 저장"에 해당한다. 정본 내보내기를
    5초 잠잠 / 마지막 참여자가 나갈 때 / 종료 때 쓰고, `meta.json` 에 덮은 seq 를 남긴다. 내려받기·보관용이며
    재생 기준으로 쓰지 않는다.
- **엔진 업그레이드:** 새 기록은 옛 엔진으로만 재생할 수 있다. 그래서 시작할 때 방의 엔진 지문이 다르면 그
  방은 세대 전환으로 시작한다.
  - `doc.<ext>` 가 마지막 seq 까지 덮고 있으면(정상 종료) 그것을 새 base 로 한다.
  - 덮지 못했으면(비정상 종료 뒤 업그레이드) 남은 기록을 새 엔진으로 재생해 보고, 서버 로그에 경고를 남긴다.
  - 어느 경우든 참여자는 지문이 바뀌었으므로 다시 들어오면서 새 welcome 을 받는다.
- **대가와 확인:** 계속 이어지는 세션은 기록이 길어진다. 늦은 참여자와 재시작한 정본의 재생 시간이 그만큼
  는다. 관문에서 다음을 잰다.
  - 중간 크기 문서에서 기록 1,000 / 10,000 묶음의 늦은 참여 재생 시간(브라우저)과 정본 복원 시간(Node).
  - welcome 크기: 기준점 + 기록이 `maxMessageBytes` 를 넘지 않게, 기록은 `catchup` 과 같은 형식으로 나눠 보낸다.
  - 10,000 묶음 재생이 5초를 넘으면 다음 단계에서 (D)를 한다.
- **(D) 정규화 연산 — 다음 단계 후보로 기록만 남긴다:** 서버가 조용할 때 `{m:"collabNormalize"}`(제자리 E→R)를
  기록에 넣으면 모두가 같은 seq 에서 기준점을 얻는다. 두 가지를 확인해야 한다.
  - 체크포인트는 정규화 때 **다시 읽은 바로 그 바이트** E(M) 이어야 한다. 그러면 "두 번째부터 고정점" 전제가
    필요 없다. 그 뒤 다시 내보낸 E(R(E(M))) 이면 이 전제가 필요하다.
  - 미확정을 그대로 통과시키려면(보정 = 항등) R∘E 가 문단·글자 인덱스를 보존해야 한다. 이번 "문단 수 차이"가
    다시 읽기 자체에서 생긴 것인지, 그 뒤 연산에서 생긴 것인지 가려 둔다.
  - 참여자마다 자기 문서를 내보내므로, 같은 모델이면 내보낸 바이트도 같아야 한다. 캐럿·시각 기록 같은 기기별
    값이 다시 읽은 모델에 남지 않는지 확인해야 한다.

## S3-4 재접속

- 끊기면 지수 백오프로 다시 붙는다. 엔진 상태(`unconfirmed`, `lastSeq`)는 그대로 둔다. 끊긴 동안의 편집은
  계속 `unconfirmed` 에 쌓인다. 화면에 "연결이 끊겼습니다. 편집은 다시 연결되면 보내집니다".
- 다시 붙을 때 `hello` 에 `lastSeq` 를 싣는다. 서버는:
  - `lastSeq` 가 기록 범위 안이면 `{type:"catchup", entries}`(그 뒤 기록) → 클라이언트는 원격 수신으로 처리
    (되감기·보정) → `requeue` → flush.
  - 범위 밖(세대 전환으로 비워짐, S3-3 결정)이면 일반 `welcome` → 재동기화(미확정 취소, 알림).
- **끊기는 순간 보낸 묶음의 운명을 모른다.** 그래서 보내는 묶음마다 `batchId`(clientId + 순번)를 붙이고 서버
  기록에도 남긴다. `catchup` 에 내 `batchId` 가 있으면 남의 편집이 아니라 **확정(ack)** 으로 처리한다(중복
  적용 방지).
- 오래 끊기면 충돌이 늘어난다(2단계 §4 규칙 그대로). 미확정이 많거나(예: 2,000건) 오래 끊기면(예: 10분)
  미리 알린다.

## 관문

- S3-1: 브라우저 엔진 2종 이상에서 digest 전부 일치.
- S3-2: 잘못된 인자·범위 초과·패닉 유발 묶음을 주입해도 거절되고 방은 계속된다. 패닉 뒤 워커 재생성.

  직전과 같음. 업그레이드 절차 시험.
- S3-4: 동시 편집 중 연결 끊기·지연 → 재접속 → 수렴. 끊기기 직전 보낸 묶음이 서버에 받아졌던 경우 중복 없음.
  오래 끊김 → 재동기화 + 알림.
- **R5 시뮬레이션 확장:** 서버 정본·무작위 연결 끊김·서버 재시작을 섞어 시드 500 × 200 에서 수렴 실패 0.
