# 공동편집 8단계: 남은 후보

7단계(`docs/collab-stage7.md`)까지로 정한 범위는 끝났다. 남은 후보를 모두 진행한다(사용자 결정, 2026-11-29).

## E1 덧붙인 서식 항목 번호 다시 매기기 (cc-rhwp-f6)

- 문제:
  - DocInfo 에 항목을 덧붙이는 state(글머리표 만들기 등)는 범위 표시를 받지 못한다(7단계 A 의 조건).
  - 범위 state 앞에 DocInfo 를 덧붙인 내 op 가 있고 남도 그사이 덧붙이면, 내 항목 번호가 밀려 다시 만들지 못하고 버린다.
  - 둘 다 "덧붙인 항목의 번호가 원격 순서에 따라 달라진다"는 같은 원인이다.
- 방향:
  - 미확정을 다시 만들거나 다시 얹을 때, 내가 덧붙인 항목을 지금 문서의 목록 끝에 다시 덧붙인다.
  - 그 항목을 가리키는 참조(문단·글자 모양 번호 등)를 새 번호로 고친다.
  - 범위 표시의 조건 "DocInfo 그대로"는 "덧붙이기만"으로 넓힌다. 서버 확인(check_range_hint)은 이미 "덧붙이기만"을 허용한다.
- 시험:
  - 동시에 서로 다른 서식 항목을 덧붙여도 양쪽 입력이 취소되지 않는다.
  - 글머리표 만들기가 범위 표시를 얻는다.
  - R5 에 DocInfo 를 덧붙이는 기능을 섞어도 수렴한다.
- 먼저 계획을 보낸다.
  - 어느 목록·참조를 다시 매기는가.
  - op 의 인자 안에 박힌 번호(예: setCharShapeRuns 의 모양 id)를 어떻게 다루는가.

## E2 큰 문서의 정본 범위 확인 비용 (cc-rhwp-3b)

- 10.7MB·383쪽에서 범위 표시 state 하나에 정본이 약 1.1초를 더 쓴다. 대부분이 적용 전 정본을 내보내 다시 읽는 일
  (`reparsed_like_current`)이다.
- 방향(조사 후 결정): 정본이 "다시 읽은 모양"을 늘 들고 있게 하는 것(세대·state 기준점에서는 이미 다시 읽은 문서이므로),
  또는 비교에 필요한 구역만 정규화하는 것.
- 조건: 판정 결과가 지금과 같아야 한다. R5 세 섞기의 숫자가 고치기 전과 똑같이 나와야 한다.

## E5 보기 권한의 읽기 전용 화면 (cc-rhwp-68, E4 다음)

- 지금 보기 권한은 입력이 문서에 닿기 전에 막히고 안내가 뜨지만, 화면은 편집할 수 있는 것처럼 보인다.
- studio 에 읽기 전용 모드를 넣어(0002) 보기 권한일 때 켠다. 막을 것은 캐럿 입력·편집 메뉴·단축키·끌어 놓기 등이다.
  - 선택·복사·찾기·인쇄·확대는 그대로 둔다.
- 클라이언트 문(엔진의 권한 판정)은 그대로 둔다. 화면이 막지 못한 경로가 있어도 문서는 바뀌지 않는다.
- E4 와 같은 0002 를 고치므로 한 세션이 차례로 한다.

## E6 Linux 브라우저 시험

- 방법은 사용자와 정한다(아래 후보).
  1. GitHub Actions(ubuntu 러너)에서 브라우저 간 시험을 돈다. 이 컴퓨터에 받을 것이 없고, 공개 저장소라 무료다.
     앞으로 올릴 때마다 도는 회귀 시험이 된다.
  2. 이 컴퓨터의 OrbStack(Docker)에서 Linux 컨테이너로 돈다. Playwright Linux 이미지 등 수 GB 를 받는다.
- 합격 조건은 3단계 S3-1 과 같다. 같은 방의 Linux Chrome·Firefox·WebKit 과 Node 정본의 digest 가 매 묶음 같아야 한다.
  Node 정본은 플랫폼과 무관하므로, macOS·Windows 에서 같은 시험이 통과했던 것과 이어진다.
